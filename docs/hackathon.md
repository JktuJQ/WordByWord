# Требования Nuclear IT Hack

Источник: [«Хахатон Ноябрь 2026.pdf»](https://drive.google.com/file/d/1_AxAHkwwtbXcoznz4oYzHFaAC_D_Qffc/view), просмотрен 6 ноября 2026 года. Номера ниже — страницы PDF. Этот документ фиксирует требования и нашу трактовку, а не статус реализации.

## Обязательный сценарий

Слайды 8–11 и 14–17 требуют Android-приложение, которое импортирует аудио из памяти устройства, локально распознаёт речь, автоматически разделяет говорящих, назначает репликам временные метки, отображает стенограмму и экспортирует результат в файл JSON.

В слайдах 9 и 17 используется термин «локальная LLM». По решению команды трактуем его как неточное обозначение локальных нейросетевых моделей обработки речи; отдельная генеративная LLM не входит в обязательный план. Это трактовка команды, не ответ организаторов. Суммаризация и прочая генеративная обработка остаются возможными расширениями.

Все этапы основной задачи выполняются на Android без интернета. Все необходимые модели должны быть на устройстве к началу проверки. Готовые модели и библиотеки разрешены. Запрещены:

- отправка аудио внешним сервисам;
- облачные API транскрибации, диаризации и обработки текста;
- перенос вычислений проверяемого сценария на сервер или компьютер;
- подмена работы модели заранее подготовленной расшифровкой.

Исследования и подготовка моделей на компьютере допустимы в разработке; результатом проверки должна быть новая обработка записи на устройстве. Сохранение ранее полученных стенограмм — функция приложения, но повторное открытие сохранённого результата не доказывает работу модели на новой записи.

## Внешний JSON

Слайды 14–15 задают корневой объект с массивом `transcript`:

```json
{
  "transcript": [
    {
      "speaker_id": "speaker_1",
      "start_ms": 1250,
      "end_ms": 4380,
      "text": "Добрый день!"
    }
  ]
}
```

| Поле | Тип | Значение |
| --- | --- | --- |
| `transcript` | array | Реплики |
| `speaker_id` | string | Устойчивый идентификатор говорящего |
| `start_ms` | integer | Начало реплики в миллисекундах |
| `end_ms` | integer | Конец реплики в миллисекундах |
| `text` | string | Текст реплики |

Сохраняем исходную временную шкалу записи и связи реплик с участниками. Переименование в интерфейсе не меняет ID. Внешняя схема не диктует формат БД и внутренние Java-типы; преобразование выполняется при экспорте. Не заменяем `speaker_id` именем участника и не выводим `null` вместо требуемой строки. Политика для неизвестного участника должна быть явно согласована в задаче экспорта, поскольку внутренний контракт допускает отсутствие ID, а слайд этого случая не описывает.

## Проверка и приоритеты

По слайду 16 эксперты устанавливают заранее предоставленный APK, импортируют три общие для команд тестовые записи, запускают транскрибацию и диаризацию, экспортируют результаты и сравнивают их с эталонами. Рассчитываются WER и RTF. Нельзя ограничивать проверку заранее подобранной собственной записью.

| Критерий, слайд 22 | Баллы |
| --- | ---: |
| Точность транскрибации | 40 |
| Точность диаризации | 25 |
| Точность временных меток | 10 |
| Скорость обработки | 10 |
| Работоспособность и UX | 10 |
| Защита решения | 5 |

Сначала обеспечиваем работающую цепочку импорт → обработка → просмотр → JSON, затем улучшаем качество текста и разделения говорящих.
Для собственных измерений фиксируем устройство, Android, запись и её длительность, эталон, версии моделей/runtime, настройки и границы измеряемого времени.
RTF считаем как время обработки / длительность записи; WER — по согласованному правилу сравнения с эталоном.
Конкретные правила нормализации текста и пороги оценки в презентации не заданы.
Для командных измерений используем [правило с учётом пунктуации](asr-quality.md); это не официальная формула организаторов.

Пунктуация, прогресс и прослушивание по реплике перечислены на слайде 18 как улучшения. Редактирование, обработка перебиваний и одновременной речи, устойчивость к шуму, оптимизация памяти и аппаратное ускорение — дальнейшие улучшения со слайда 19. Переименование и повторное открытие сохраняем как продуктовые цели команды, но не ставим выше обязательного JSON-экспорта.

## Материалы для сдачи

По слайдам 20–21 в git-репозитории должны быть доступны:

- APK приложения;
- исходный код;
- инструкция установки и использования, включая подготовку моделей для офлайн-запуска;
- описание архитектуры и применяемых моделей;
- известные ограничения;
- результаты собственных тестов;
- видео работы приложения.

Организаторы просят придерживаться [шаблона репозитория](https://github.com/grigorevmp/hacathon_template): в нём есть `src`, `config`, `docs`, `artifacts` и `README.md`. При подготовке сдачи сопоставляем материалы с этой структурой; существующий Android-модуль `app/` ради названия папки не переносим. Пути к реальному коду, APK, моделям и отчётам нужно явно указать в инструкции. Ссылка на CI Artifact с ограниченным сроком хранения не заменяет долговременную доступность сдаваемого APK.

Участники должны понимать архитектуру, модели, ограничения и результаты тестов, в том числе для кода, написанного агентами (слайды 12 и 22).

## Что ещё неизвестно

- Дедлайн и канал отправки ссылки на репозиторий.
- Форматы, длительность, языки записей, число говорящих и целевое устройство проверки.
- Точные правила расчёта метрик, нормализации текста и сопоставления ID говорящих.

Не выдаём эти сведения за принятые ограничения. Вопросы и ответы организаторов дописываем с источником.
