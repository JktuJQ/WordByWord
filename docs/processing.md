# Выполнение обработки

Реализация #8 разделяет обработку и файловые операции; для экспериментального режима предусмотрен третий исполнитель в `WordByWordApplication`:

- `wbw-processing` — одна запись за раз: подготовка PCM, ASR/VAD, ожидание диаризации, сборка реплик и сохранение результата.
- `wbw-diarization` — диаризация одновременно с ASR/VAD той же записи при `parallelInference=true`.
- `wbw-io` — импорт, экспорт, загрузка библиотеки, переименование и удаление. Длительный инференс не занимает эту очередь.

Состояние `AppController` и уведомления UI применяются в главном потоке через Handler. Файловый репозиторий один на приложение; его синхронизация сохраняет атомарность операций между исполнителями. Длительное копирование может задержать другую файловую операцию и финальное сохранение, но не удерживает репозиторий на время инференса. Экспорт работает с неизменяемым снимком стенограммы.

## Конвейер и ресурсы

`LocalTranscriptionPipeline` готовит PCM один раз, затем запускает ASR/VAD и диаризацию. Экспериментальный режим выполняет их одновременно. Каждый потребитель открывает собственный reader того же PCM. Сборка через `OverlapTranscriptAssembler` начинается после завершения обеих моделей. PCM закрывается только после возврата обеих задач, включая ошибку и отмену. В хранилище попадает только целиком завершённая стенограмма.

Ошибка одной модели кооперативно останавливает вторую. Не прерываем JNI принудительно и не закрываем аудио до его возврата. Если пользователь отменил обработку, отмена имеет приоритет над последующей ошибкой; иначе сохраняем исходную ошибку модели, а не вызванную ею отмену соседа.

UI показывает этапы ASR и диаризации вместе с доступными процентами каждого. Общий индикатор остаётся неопределённым: измеренной модели длительности этапов пока нет.

Для контрольной сборки доступен `-PparallelInference=false`: исполнитель диаризации выполняется в вызывающем потоке, затем идёт ASR. По умолчанию `parallelInference=false`: текущий контрольный прогон не показал ускорения. Сравнение времени и памяти описано в [evaluation/README.md](../evaluation/README.md).

## Отмена и конкурентные действия

Отмена проверяется до подготовки/запуска моделей и между этапами и внутри совмещения реплик. Чтение PCM и ASR проверяют её внутри своей работы; один блокирующий JNI-вызов sherpa не прерывается. Пока вызов не вернулся и ресурсы не освобождены, задача остаётся занятой, повторный запуск не допускается. Если отмена уже запрошена, последующая ошибка модели считается завершением отмены.

Финальное сохранение — точка фиксации: если задача уже перешла к атомарной записи результата, отмена не принимается. Это исключает ситуацию, когда готовый результат сохранён, но UI сообщает об отмене. Ошибка постановки задачи в исполнитель освобождает состояние занятости и позволяет повторить запуск.

Обрабатываемую запись удалять нельзя, включая время ожидания отмены. Другие записи можно импортировать, просматривать, экспортировать, переименовывать и удалять во время обработки. Смешанный набор удаления с текущей записью отклоняется целиком. Во время незавершённого удаления запуск новой обработки блокируется; уже работающая обработка другой записи продолжается. Готовая стенограмма открывается существующим UI; отдельную кнопку повторной обработки готового результата этот этап не добавляет.

## Жизненный цикл и ограничения

Контроллер и исполнители принадлежат Application, поэтому пересоздание Activity не запускает задачу заново. При уходе экрана подписчик UI отсоединяется, обработка продолжается, пока жив процесс. Foreground service и WorkManager не добавлены: выполнение в фоне, после удаления приложения из списка недавних или после завершения процесса не гарантируется. После перезапуска восстанавливаются импорт и завершённые результаты, незавершённая задача автоматически не возобновляется.

Целевая среда — эмулятор. Launcher `nix run .#start-emulator` задаёт 4 ГБ RAM и `vm.heapSize=256`, в том числе для существующего профиля при следующем запуске. Объём RAM Android не равен Java heap приложения; фактические лимиты зависят от системного образа. Обрабатывается одна запись, внутри неё две модели могут держать ресурсы одновременно. Диаризация читает весь PCM в `float[]`: 16 000 × 4 байта на секунду только для этого массива, плюс Java/JNI и ОС. Измерение короткой записи не гарантирует размещение произвольной длительности в памяти.


JVM-тесты проверяют этапы и освобождение PCM, отмену, повторный запуск и работу I/O при заблокированной обработке на настоящих потоках. Они не заменяют сквозной запуск моделей на Android, проверку памяти и ручную проверку сворачивания.

## Контрольный прогон 7 ноября 2026

ASR GigaAM v2 int8, Silero VAD; диаризация использует поставляемые модели. Лимит процесса эмулятора на хосте: 4 ГиБ, без host swap, CPUQuota=200%. Между режимами эмулятор перезапускался, поэтому это одиночные предварительные прогоны, а не устойчивый сравнительный бенчмарк. Будущая конфигурация launcher на 4096 МиБ здесь не проверялась.
