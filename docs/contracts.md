# Общие контракты MVP

Предложение для Issue [#1](https://github.com/JktuJQ/WordByWord/issues/1).
Перед интеграцией реализации контракт проверяет один из его потребителей.
Здесь определены границы компонентов; устройство их внутреннего кода остаётся
за авторами. Реализаций обработки, БД, плеера и UI в этом изменении нет.

Код: `app/src/main/java/dev/wordbyword/app/core/`. Это обычная Java без Android,
JNI, Room и сторонних библиотек. `record` используются как неизменяемые снимки
данных; списки внутри них копируются. JDK для сборки остаётся заданным в flake,
уровень языка приложения — Java 17.

## Данные

| Тип | Назначение |
| --- | --- |
| `Recording` | ID записи, непрозрачный URI исходного аудио, заголовок и длительность, если известна |
| `TimeRange` | Интервал `[startMs, endMs)` в миллисекундах от начала исходной записи |
| `RecognitionResult` | Полный текст и доступные временные фрагменты с явной точностью: слово, токен, сегмент или без таймкодов |
| `TimedText` | Текст одного временного фрагмента распознавания |
| `SpeakerSegment` | Интервал диаризации и ID говорящего |
| `Speaker` | Устойчивый ID участника в пределах записи и изменяемое пользователем отображаемое имя |
| `Utterance` | Интервал, текст и необязательный ID участника |
| `Transcript` | Участники и собранные реплики одной записи |
| `RecordingTranscript` | Запись вместе с сохранённой стенограммой |

ID — непрозрачные строки. Не требуется UUID, числовая последовательность или
одинаковое обозначение одного человека в разных записях. Один `speakerId` может
означать разных людей в разных записях. Переименование меняет `displayName`,
а не ID и не связи реплик. Неизвестный говорящий — `Optional.empty()`;
определённый ID должен присутствовать в списке участников этой стенограммы.

Все интервалы относятся к исходному аудио. VAD, нарезка и другие преобразования
не должны сдвигать реплики к началу отдельного фрагмента или удалять паузы из
общей шкалы. Диаризационные интервалы могут пересекаться. Нулевой интервал
допустим для точки; отрицательные и обратные интервалы недопустимы.

Таймкоды моделей не считаются точными по умолчанию. Полный распознанный текст
может существовать без временных фрагментов (`UNAVAILABLE`). Токены не выдаются
за слова. Как сопоставлять сегментный текст, неизвестных говорящих и пересечения,
решает реализация сборщика; ограничения требуется описать при интеграции.
Сборщик выдаёт реплики в хронологическом порядке; одинаковое начало и пересечения
разрешены. Хранилище сохраняет этот порядок.

## Подготовленное аудио

`PcmAudio` — повторно читаемый источник PCM 16 кГц, моно, с нормализованными
`float`-отсчётами в `[-1, 1]`. Это обменный формат, а не требование хранить всё
аудио массивом или в определённом формате файла. Внутри адаптера модели данные
можно преобразовать к нужному ему представлению.

`openReader()` каждый раз открывает чтение с начала. `Reader.read()` получает
буфер от потребителя и возвращает фактическое число отсчётов либо `-1` на EOF.
Число отсчётов может быть неизвестно заранее. Пропуск пауз в этом источнике
не допускается: сохраняется исходная временная шкала.

Владелец закрывает каждый reader, затем `PcmAudio`. Адаптеры ASR и диаризации
могут открывать собственные readers, но не закрывают сам источник. Закрытие
источника освобождает его временные ресурсы, не удаляя исходную запись.
Файл, память, кеш, способ декодирования и ресэмплинга остаются деталями реализации.

## Границы обработки

- `AudioPreparer`: URI исходного аудио → `PcmAudio`.
- `SpeechRecognizer`: `PcmAudio` → `RecognitionResult`.
- `SpeakerDiarizer`: `PcmAudio` → список `SpeakerSegment`.
- `TranscriptAssembler`: результаты распознавания и диаризации → `Transcript`.
- `TranscriptionPipeline`: `Recording` → законченный `Transcript`.

Методы блокирующие. Это позволяет проверить адаптер отдельно и не навязывает
команде Futures, Rx, Android Service или конкретный executor. Вызывать их
нужно вне главного потока Android. Последовательность этапов, VAD, степень
параллелизма и время жизни экземпляров выбирает реализация конвейера.

`ProcessingContext` передаётся вызывающей стороной:

- `isCancellationRequested()` сообщает об отмене; `throwIfCancelled()` бросает
  стандартную `CancellationException`.
- `reportProgress()` получает ключ этапа и необязательную долю `0..1` этого этапа.
  Ключи этапов определяет реализация и согласует с UI; жёсткого enum или общего
  взвешивания этапов нет. Прогресс может быть неопределённым.

Контекст должен безопасно принимать вызовы из рабочих потоков. Колбэк прогресса
исполняется на вызывающем рабочем потоке; доставку в UI организует его адаптер.
Отмена кооперативная: проверяется между доступными единицами работы, без обещания
немедленно прервать один вызов JNI. Подготовленные ресурсы закрываются и при отмене.

Пустой успешный `Transcript` означает отсутствие реплик, а не ошибку/отмену.
`ProcessingException` описывает сбой и сохраняет исходную причину. Классификацию
ошибок, повторные попытки и пользовательские сообщения этот контракт не задаёт.
При ошибке или отмене успешный результат не возвращается. Частичные результаты
не входят в текущую границу конвейера; streaming остаётся отдельной задачей.

## Хранение

`TranscriptRepository` предоставляет список записей, поиск по ID, сохранение
полного результата и переименование участника одной записи. Это блокирующие
операции вне UI-потока. `find()` возвращает пустой `Optional`, если записи нет.
Ошибки хранения передаются через `IOException` с сохранением причины;
переименование несуществующей записи/участника — `NoSuchElementException`.

`save()` сохраняет результат под ID записи и обеспечивает долговечный доступ
к исходному аудио, например копируя его в приватное хранилище. Он возвращает
актуальный `RecordingTranscript` с URI, которым управляет хранилище. Старый
внешний URI нельзя молча считать долговечным. При сбое частичное сохранение не
выдаётся за завершённое. Конвейер сам не сохраняет результаты: это делает
вызывающий компонент после успеха.

Room, JSON, схема БД, сериализация, физические пути, транзакции и поддержка
конкурентных вызовов определяются реализацией. Условия конкурентного доступа
нужно описать при её подключении. Подготовленный PCM хранить постоянно не требуется.

## Пример: два участника

```java
var recording = new Recording(
    "meeting-1", URI.create("content://example/audio/7"), "Встреча", OptionalLong.of(6000));
var transcript = new Transcript(
    List.of(new Speaker("a", "Участник 1"), new Speaker("b", "Участник 2")),
    List.of(
        new Utterance(Optional.of("a"), "Начнём?", new TimeRange(1000, 2000)),
        new Utterance(Optional.of("b"), "Да, начнём.", new TimeRange(2500, 4000))));

// После обработки: сохранение и переименование идут через тот же repository.
RecordingTranscript saved = repository.save(recording, transcript);
repository.renameSpeaker(saved.recording().id(), "a", "Анна");
```

В другом разговоре участник `a` не обязан быть Анной. Конкретный URI в примере —
только иллюстрация: контракт не требует Android content URI от всех реализаций.

## Что остаётся открытым

Выбор runtime/моделей, UI-дизайн, модели потоков, Service/WorkManager, БД,
идентификаторы этапов, ограничения длительности, алгоритм совмещения и конкретные
адаптеры не определены этим PR. На проверке моделей нужно подтвердить реальный
формат таймкодов. Перед реализацией потребители проверяют подходящий им интерфейс;
добавлять методы можно отдельными согласованными изменениями.

Проверка контрактов: `./gradlew testDebugUnitTest assembleDebug lintDebug` внутри
`nix develop path:.`. JUnit используется только в JVM-тестах, не в приложении.
