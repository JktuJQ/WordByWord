# Общие контракты MVP

Предложение для [#1](https://github.com/JktuJQ/WordByWord/issues/1).
Перед интеграцией интерфейсы проверяют их потребители. Реализаций обработки,
хранилища и новых экранов здесь нет. Контракты используют обычную Java 17.

## Пакеты

В `app/src/main/java/dev/wordbyword/app/core/`:

| Пакет | Содержимое |
| --- | --- |
| `recording` | `Recording`: ID, URI исходного аудио, название, необязательная длительность |
| `audio` | `AudioPreparer` и повторно читаемый `PcmAudio` |
| `recognition` | `SpeechRecognizer`, `RecognitionResult` с вложенными `Segment` и `Timing` |
| `diarization` | `SpeakerDiarizer` с вложенным `Segment` |
| `transcript` | `Transcript` с вложенными `Speaker` и `Utterance`, `TranscriptAssembler` |
| `processing` | Общий контекст, ошибка обработки и интерфейс конвейера |
| `storage` | `TranscriptRepository` |

Небольшие связанные данные сгруппированы внутри результата. Отдельных классов
для временного интервала, события прогресса и обёртки сохранённого результата нет.
Списки внутри `Transcript` и `RecognitionResult` копируются в неизменяемые снимки.
Record-конструкторы не заменяют проверку результатов моделей и пользовательского ввода.

## Общие правила данных

- `startMs`, `endMs` — интервал `[startMs, endMs)` в миллисекундах от начала
  **исходной** записи; `0 <= startMs <= endMs`. Подготовка аудио и VAD сохраняют
  эту шкалу. Диаризационные интервалы могут пересекаться.
- ID — непрозрачные строки. `speakerId` устойчив только внутри одной записи.
  Переименование меняет имя, сохраняя ID и связи реплик. Для неизвестного
  участника используется `Optional.empty()`; известный ID присутствует в `speakers`.
- `Transcript` уже содержит `Recording`, поэтому сохранение и чтение используют
  один тип. URI непрозрачен: способ доступа определяет адаптер аудио/хранилища.
- `RecognitionResult.Timing` честно обозначает слова, токены, сегменты либо
  отсутствие таймкодов. При `UNAVAILABLE` список сегментов пуст; текст может быть
  непустым. Сборщик определяет политику совмещения, используя также метаданные записи.
- Итоговые реплики идут в хронологическом порядке. Пустая стенограмма означает
  успешное отсутствие речи, а не ошибку или отмену.

## Аудио и обработка

`AudioPreparer.prepare()` возвращает PCM 16 кГц, моно: нормализованные `float`
в `[-1, 1]`, включая паузы исходной записи. Это обменный формат, не требование
держать весь файл в памяти. Адаптер модели может преобразовать его для своего runtime.

Каждый `PcmAudio.openReader()` начинает чтение с нулевого отсчёта. `read()`
возвращает положительное число прочитанных отсчётов, `-1` при EOF и `0` только
при запросе нулевой длины. Общее число отсчётов может быть неизвестно.
Владелец закрывает readers, затем источник. ASR/диаризация закрывают свои readers,
но не общий источник. Освобождаются временные ресурсы, не исходная запись.

`SpeechRecognizer.transcribe(PcmAudio audio, ProcessingContext context)` возвращает
`RecognitionResult` и при ошибке выбрасывает `ProcessingException`. Прежнее имя
`recognize` заменено на `transcribe`. Распознаватель не закрывает переданный `PcmAudio`,
но закрывает открытые им readers. Для Silero VAD + GigaAM результат имеет
`Timing.SEGMENT`: интервалы относятся к исходной записи и включают контекст VAD,
это не таймкоды отдельных слов. При отсутствии речи возвращаются пустой текст и
пустой список сегментов; отмена передаётся через `CancellationException`.

Интерфейсы обработки блокирующие; вызывать их нужно вне главного потока Android.
`TranscriptionPipeline` возвращает готовый `Transcript`; сохранение выполняет
вызывающая сторона. VAD, порядок этапов, executor, Service и параллелизм выбирает реализация.

`ProcessingContext` передаёт отмену и прогресс без отдельного объекта события.
Ключ этапа согласуется с UI; доля `0..1` относится к этому этапу, пустой
`OptionalDouble` означает неопределённый прогресс. Контекст поддерживает вызовы
из рабочих потоков; доставку колбэков в UI организует адаптер.
Отмена кооперативная, с `CancellationException`, без обещания прервать один вызов JNI.
Ошибки передаются через `ProcessingException` с исходной причиной. При сбое/отмене
успешный результат не возвращается, временные ресурсы освобождаются.

## Хранение

Обязательный внешний JSON-экспорт описан в [hackathon.md](hackathon.md).
Это отдельное представление результата, не схема внутреннего хранения.
Экспорт использует `transcript`, `speaker_id`, `start_ms`, `end_ms`, `text`;
имя участника не подменяет его ID. Политику для отсутствующего внутреннего
`speakerId` нужно согласовать при реализации экспорта: внешний формат требует строку.

`TranscriptRepository` даёт список записей, поиск, сохранение записи и полной
стенограммы, а также атомарное обновление через преобразование. `saveRecording()` регистрирует импорт до
запуска обработки, поэтому ошибка конвейера не удаляет саму запись.
`saveRecording()` возвращает запись с URI приватной копии исходного файла и не удаляет готовую стенограмму при повторном вызове. `delete()` удаляет запись вместе с аудио и стенограммой; повторное удаление безопасно.
`renameRecording()` атомарно меняет название записи, сохраняя аудио и существующую стенограмму.
Метод работает и до обработки, не создавая пустую стенограмму.
`find()` возвращает пустой `Optional`, если готовой стенограммы нет (в том числе у ещё не обработанного импорта). `save()` сохраняет полный
результат под ID записи, обеспечивает доступ к исходному аудио после перезапуска
и возвращает `Transcript` с долговечным URI, которым управляет хранилище.
Частично сохранённый результат не выдаётся за завершённый.

Операции блокирующие, вне UI-потока. Ошибки хранения — `IOException` с причиной;
переименование отсутствующей записи/участника — `NoSuchElementException`.
Переименование затрагивает только указанную запись. Поддержку конкурентных вызовов
описывает реализация. Контракт не предписывает Room, JSON, схему БД, физические пути и транзакции. Текущая файловая реализация и её гарантии описаны в [storage.md](storage.md).

## Пример двух участников

```java
var recording = new Recording(
    "meeting-1", URI.create("content://example/audio/7"), "Встреча", OptionalLong.of(6000));
var transcript = new Transcript(
    recording,
    List.of(new Transcript.Speaker("a", "Участник 1"), new Transcript.Speaker("b", "Участник 2")),
    List.of(
        new Transcript.Utterance(Optional.of("a"), "Начнём?", 1000, 2000),
        new Transcript.Utterance(Optional.of("b"), "Да, начнём.", 2500, 4000)));

Transcript saved = repository.save(transcript);
Transcript renamed = repository.update(saved.recording().id(), current ->
    new TranscriptEditor(current)
        .renameSpeaker("a", "Анна")
        .renameSpeaker("b", "Борис")
        .build());
```

Это только пример данных. Конкретные runtime/модели, алгоритм совмещения, БД,
дизайн UI, ограничения файлов и механизм фоновой работы выбираются в своих задачах.
Изменения общих интерфейсов согласуются с потребителями.

Проверки в Nix devShell: `./gradlew testDebugUnitTest assembleDebug lintDebug`.
JUnit подключён только к JVM-тестам, не к приложению.

Изменения готовит `TranscriptEditor`: `renameSpeaker` возвращает редактор для цепочки вызовов, `build()` создаёт независимый снимок. `TranscriptRepository.update` атомарно читает актуальную стенограмму, применяет синхронное преобразование и сохраняет результат. При ошибке весь набор изменений отменяется. Преобразование не должно выполнять I/O или повторно обращаться к репозиторию; изменение ID записи запрещено. JSON-кодеки находятся в пакете `json`, файловые операции принадлежат репозиторию.
