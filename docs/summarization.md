# Прототип суммаризации (#54)

Первый этап проверяет загрузку модели и генерацию из Java на Android. Зависимость
LiteRT-LM подключена только к `androidTestImplementation`; в пользовательский APK
она пока не входит. Интерфейс, сохранение выжимки и обработка длинных стенограмм
ещё не реализованы: сначала нужно получить приемлемое качество модели.

## Конфигурация

- LiteRT-LM Android 0.17.1, CPU, контекст 1280 токенов, ответ до 256 токенов.
- Модель: `litert-community/Qwen3-0.6B-int4`,
  `qwen3_0.6b_nothink_q4_block32_ekv1280.litertlm`.
- Ревизия: `56621f0115eba5781051ef9714c06e16e6d40c0b`.
- Размер файла: 347251840 байт.
- SHA-256: `2df6821ec12702dafd33915e7a1a1adc7c4b053f3672fd9555dfaf3a114c4139`.
- В карточке модели и у базовой Qwen3 заявлена Apache-2.0. Перед распространением
  весов нужно включить требуемые лицензионные материалы.

Источники: [артефакт и настройки](https://huggingface.co/litert-community/Qwen3-0.6B-int4),
[базовая модель](https://huggingface.co/Qwen/Qwen3-0.6B),
[API LiteRT-LM](https://ai.google.dev/edge/litert-lm/android).

Java callback проверен реальным запуском. `EngineConfig` в 0.17.1 требует полного
конструктора из семи аргументов; `extraContext` у `sendMessageAsync` не допускает
`null`. Kotlin и корутины присутствуют в зависимостях библиотеки.

Версия 0.19.1 тоже собрала тестовый APK, но не запускалась: lint сообщил о Kotlin
metadata 2.4 при ожидаемой 2.2. В 0.17.1 аналогичные сообщения остались у
транзитивного `kotlin-reflect:2.4.0`. Задача lint завершается успешно, однако
совместимость анализатора нужно решить до включения зависимости в приложение.
Понижать транзитивные зависимости без проверки их совместимости не стали.

## Воспроизведение

Войти в `nix develop`. Модель скачать до запуска проверки:

```sh
mkdir -p local-models
curl -fL 'https://huggingface.co/litert-community/Qwen3-0.6B-int4/resolve/56621f0115eba5781051ef9714c06e16e6d40c0b/qwen3_0.6b_nothink_q4_block32_ekv1280.litertlm' -o local-models/summary.litertlm
bash evaluation/summarization-prototype.sh emulator-5556 local-models/summary.litertlm
```

Заменить serial на нужный из `adb devices -l`. Скрипт проверяет SHA-256, собирает
APK, обновляет приложение и тестовый APK без очистки данных, копирует модель и
запускает три генерации с отдельной загрузкой/закрытием Engine. Для сопоставимости
закрыть приложение перед прогоном; не выполнять параллельно ASR и диаризацию.

Тест явно проверяет отсутствие INTERNET-разрешения у целевого приложения. Для
финальной проверки на телефоне дополнительно отключить сеть перед запуском
инструментирования с заранее установленными APK и моделью.

В `evaluation/results/summarization54/` сохраняются вывод инструментирования,
JSON с ответами и временем, память устройства, commit и diff. Каталог исключён
из Git. У каждого запуска своё имя отчёта, чтобы авария процесса не позволила
принять предыдущий файл за новый результат. Нативный краш может не оставить JSON;
ошибку нельзя считать успешным тестом. Без `-e runSummary true` тест пропускается.

`pss_kb_after_generation` — снимок PSS после ответа, не пиковое значение.
`VmHWM` из `process_status` — максимум RSS процесса с его запуска; повторные
генерации одного процесса не дают независимых пиков. Для окончательной оценки
нужен отдельный мониторинг пиков PSS и проверки на физическом телефоне.

## Результаты 2026-11-08

Эмулятор `sdk_gphone64_arm64`, Android 16 / API 36, MemTotal 2021944 КБ,
до запуска MemAvailable около 830548 КБ. Это не измерение скорости телефона.
Два эксперимента по три генерации короткого синтетического разговора; исходный
текст и промпт доступны в тесте/локальных JSON. Это настройка, не независимая
оценочная выборка. Проверка непустого ответа подтверждает работу API, не качество.

Первый промпт просил 3–5 предложений. Загрузка: 540–660 мс, генерация: 1145–1546 мс;
наибольший VmHWM: 972664 КБ (около 950 МиБ). Во всех трёх ответах пропущены время
встречи 15:00, бюджет 120 тысяч и отказ покупать сервер; фраза «Анна проверила сроки»
искажает исходное сообщение о переносе встречи.

Второй промпт явно запросил факты отдельными пунктами с числами, сроками и
запретами. Загрузка: 522–665 мс, генерация: 1486–1865 мс. Время и сумма появились,
но во всех трёх ответах модель написала «Анна и Ольга сделали проверку» и «Ольга
пришла завтра» вместо будущей отправки результатов проверки; запрет покупки
сервера снова потерян. Три повтора внутри каждого эксперимента совпали по тексту.

Предварительный вывод: совместимость Java/Android и повторные запуски подтверждены;
качество первых двух промптов на данном примере недостаточно. Перед UI-интеграцией
нужна проверка промптов и при необходимости других кандидатов с ручной
оценкой фактов. Физический телефон пока не подключён. Сохранение, отмена,
длинный текст и итоговый офлайн-сценарий приложения остаются в работе #54.

## Сравнение промптов после первого эксперимента

По уточнению пользователя проверены ещё три варианта на трёх коротких
синтетических разговорах: исходная инструкция, строгий список фактов и инструкция
с одним примером другого разговора и конспекта. Всего девять генераций, та же
модель и runtime. Первый разговор уже использовался при настройке; два новых
проверяют перенос даты, незавершённые действия, запреты и отвергнутое предложение.
Пример в промпте не содержит ответы на проверяемые разговоры. Это по-прежнему
разработка промпта, а не независимый итоговый benchmark.

Для воспроизведения:

```sh
SUMMARY_COMPARE=true bash evaluation/summarization-prototype.sh emulator-5556 local-models/summary.litertlm
```

| Промпт | Первый разговор | Перенос запуска | Аренда ноутбуков |
| --- | --- | --- | --- |
| Исходный | Искажения и пропуски | Потеря точных дат | Потеря чисел и деталей |
| Строгий список | Есть сумма и запрет, потеря срока сметы | Придуманы привязки фактов к 19 мая | Перестановка авторов, выдуманная реплика «Укажите новую дату» |
| С примером | Сохранены все шесть исходных сообщений | Практически повторён исходный текст | Скопированы инструкции, потерян факт о невыбранном поставщике |

Промпт с примером улучшил сохранение фактов, но модель преимущественно копирует
текст вместо сжатия. Время генерации этого варианта — 1816–2054 мс на эмуляторе.
Вывод о необходимости сразу сменить модель был преждевременным. Следующая
проверка — настройка промпта с примером на более длинном тексте с повторами и
оценка как точности фактов, так и степени сжатия на отдельных разговорах.

Состав проверенных APK: основной `app-debug.apk` (около 268 МиБ) содержит ASR,
Silero VAD и обе модели диаризации; тестовый APK (около 73 МиБ) содержит нативный
runtime LiteRT-LM. Веса LLM (347251840 байт) находятся отдельно в каталоге приложения
после `adb push`. Единого APK со всеми весами и пользовательской суммаризацией
на этом этапе нет.

## Разделение настройки и контроля

Следующий эксперимент: `SummaryPromptStudy` содержит два новых промпта и отдельный
контрольный разговор о библиотеке. Три прежних разговора остаются development;
никакие их результаты больше не считаются независимой проверкой. Пример в новом
промпте — экскурсия и обход закрытого моста, с другими персонажами и фактами.

До просмотра ответов зафиксирован порядок: сравнить два промпта только на
development, выбрать по фактической точности, полноте и отсутствию копирования
инструкций; при равенстве предпочесть более короткий. Затем один раз запустить
выбранный вариант на контроле без дальнейшей настройки по его ответу. Если после
этого менять промпт, контроль становится частью development и требуется новый
контрольный разговор.

Для контроля заранее проверяем: итоговую дату и время, предел числа участников,
бесплатность, ответственного и срок объявления, запрет печати, ответственного и
срок проверки проектора, неопределённость его исправности. Отдельно отмечаем
выдуманные факты, старую дату как действующую, потерю отрицаний, попадание примера
или инструкции в ответ и степень сжатия. Критерии/эталон не передаются модели.
Это синтетический контроль, написанный разработчиком; один такой пример не
подтверждает качество на настоящих стенограммах ASR.

По development выбран `SummaryPromptStudy.PROMPTS[0]`: короткая инструкция без
примера. Оба новых варианта ошибаются, но вариант с экскурсией переносит посторонние
факты в ответы двух разговоров и искажает третий. Выбор лучшего из этих двух не
означает приемлемого качества. Выбор сделан до просмотра контрольного ответа;
проверяется один запуск с `promptHoldout=true`, `selectedPrompt=0`.

Контроль выполнен один раз, генерация 2295 мс на эмуляторе. Итоговая дата и время,
бесплатность, срок текста и проверка проектора во вторник сохранены. Однако модель
выдумала «Лев пригласит 16 человек», написала «приложение не будет печатать» и
потеряла неопределённость исправности проектора. Контроль не пройден по фактической
точности. После просмотра ответа промпт не менялся.

Настройка запускается через `SUMMARY_STUDY=true`, контроль — через
`SUMMARY_HOLDOUT=true SUMMARY_PROMPT=0` перед командой скрипта. Эти режимы нельзя
считать независимыми при повторной настройке на уже просмотренном контроле.
Данные синтетические; следующим отдельным контролем должна стать настоящая
стенограмма, не использованная в промптах или настройке. Все три development-текста
и контрольный текст доступны в исходниках Android-теста; ответы хранятся локально
в `study-development.json` и `study-holdout.json` каталога результатов.

## Проверка на Dialogs из evaluation

Зафиксированный `SummaryPromptStudy.PROMPTS[0]` применён без настройки к текстам
трёх файлов `fixtures/dialogs/manifest.json` и к сохранённым гипотезам
`results/dialogs/asr-hypotheses.json`. ASR заново не запускался; сохранённые тексты
не содержат назначения говорящих и пунктуации. Источник и ограничения записей —
[SOURCE.md](../evaluation/fixtures/dialogs/SOURCE.md): составленные разговоры из
реальных голосов актёров, исходный текст независимо не прослушан. Кулинарные
разговоры пересекаются по репликам, поэтому это не три независимых разговора.

Входной массив сохранён в `evaluation/results/summarization54/dialogs-inputs.json`,
SHA-256 `971f8edbe710aa36f6bea71aa95af7d349e153d1d0432157276c01b02831fc51`.
Порядок: для каждого файла исходный текст, затем ASR-гипотеза; всего шесть входов
по 830–1093 символа. На этом этапе сравниваем смысл и ошибки выжимки, не DER/WER.
Режим теста — `summaryCorpus=true`; массив перед запуском копируется в
`summary-corpus.json` каталога external files целевого приложения. В модель
передаётся только поле `text`, а не эталоны оценки или имена файлов.

Все шесть генераций завершились, Android-тест прошёл за 19,823 с. Проверка теста
подтверждает успешное получение непустых ответов, не их смысловую правильность.

| Файл | Генерация upstream / ASR, мс | Ручная проверка |
| --- | --- | --- |
| dialogs_md | 2419 / 2046 | Тема весны и прогулок передана. В upstream потеряно предложение прогулки на выходных; ASR-вариант его сохранил. Есть бессмысленные обрывки «Погода и одея», лишние приветствия. |
| dialogs_ms | 3035 / 2823 | В upstream модель приписала пад-таю курицу и овощи из описания рамена. В ASR-варианте написала «Варя в блендере», хотя пасту варят отдельно, а соус смешивают в блендере. |
| dialogs_msd | 3254 / 2464 | В upstream авокадо и лосось перенесены из суши в пасту и пад-тай, появились повторы. В ASR-варианте возникли «Суши с паттай» и «Суши с раман», которых во входе нет. |

Пример точного ответа на исходный dialogs_ms:

> - Рецепт пад тай с курицей и овощами.
> - Рецепт рамен с курицей и овощами.

В исходнике состав пад-тая не описан; курица и овощи относятся только к рамену.
Это ошибка суммаризации, присутствующая до влияния ошибок ASR. На данном
зафиксированном промпте общая тема распознаётся, но точность деталей недостаточна.
Промпт по этим ответам не менялся. Любая следующая настройка с учётом этих ошибок
переводит Dialogs в development; для следующей чистой проверки нужен другой
разговор, без пересекающихся реплик. Полные входы, промпты и ответы находятся в
`evaluation/results/summarization54/dialogs-summary.json`.
