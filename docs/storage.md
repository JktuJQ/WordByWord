# Постоянное хранение

Реализация #9 — `storage/FileTranscriptRepository`, выбранная по согласованию с владельцем задачи. Новых зависимостей нет: JSON обрабатывает существующий Gson 2.15.0. `WordByWordApplication` создаёт один репозиторий и передаёт его всем потребителям; `DemoBackend` остаётся только демонстрационным конвейером в приложении и in-memory заглушкой для JVM-тестов.

## Формат и владение

Данные находятся в `filesDir/library/<sha256(recordingId)>/`:

- `audio` — побайтовая копия исходного файла, без декодирования или конвертации;
- `recording.json` — UTF-8 JSON версии 1: ID, название, URI, необязательная длительность, а для завершённого результата — участники и реплики.

Хеш ID используется только как безопасное имя папки. ID записи и участников сохраняются без изменений. Отображаемые имена отделены от speakerId. Пустой список реплик является готовой стенограммой тишины; отсутствие полей стенограммы означает импорт, который ещё можно обработать. Встроенный пример имеет явный `demo://` URI, не содержит аудио и остаётся вымышленным примером интерфейса.

Это внутренний формат хранения. Экспорт по схеме организаторов не меняется. Поля и целочисленные интервалы проверяются при чтении и перед записью; неизвестная версия отвергается без перезаписи файла. Миграций других версий пока нет. URI файла восстанавливается относительно папки репозитория, а не используется как произвольный путь из JSON.

`AudioDocuments` вызывает `saveRecording` в рабочем потоке непосредственно при импорте. Он добавляет запись в UI только после успешного копирования. После этого исходный документ можно удалить или отозвать доступ к нему: приложение работает с собственной копией. Постоянное SAF-разрешение не требуется. При успешном приёме записи встроенного диктофона его исходный файл в приватной папке `recordings` удаляется; при ошибке копирования исходник сохраняется. Произвольные пользовательские файлы не удаляются.

PCM-декодер получает URI сохранённого оригинала и продолжает владеть только своими временными PCM-файлами. Промежуточный PCM в библиотеку не попадает. Копирование аудио идёт потоково, без загрузки всего файла в память.

## Запись, ошибки и удаление

Новый импорт сначала создаётся в `.pending-*` внутри того же файлового хранилища. После успешного копирования аудио, синхронизации содержимого файлов и записи метаданных папка атомарно переименовывается в окончательную. При ошибке импорта запись не публикуется; временная папка удаляется.

Метаданные и стенограмма сначала записываются в `.metadata-*.tmp`, файл синхронизируется и атомарно заменяет `recording.json`. Ошибка до замены сохраняет предыдущий результат. Отдельная неуспешная обработка не удаляет исходный импорт. При нехватке места или другом I/O-сбое исключение доходит до вызывающего кода, который показывает ошибку вместо успешного сохранения. Поддержка файловой системой атомарного переименования обязательна; небезопасного fallback нет. Гарантия относится к прерыванию процесса, а не к любому отказу накопителя или питания.

Удаление сначала атомарно переименовывает папку в `.trash-*`, затем освобождает файлы. После переименования запись уже не входит в библиотеку. Если очистка мусора не удалась, ошибка записывается в лог и удаление файлов повторяется при следующей загрузке. Оставшиеся `.pending-*`, `.trash-*` и временные метаданные также очищаются при загрузке. Повреждённые пользовательские записи автоматически не удаляются.

Нечитаемые метаданные пропускаются с сообщением пользователю и записью причины в лог; остальные записи загружаются. Если метаданные доступны, а аудио отсутствует, карточка появляется с ошибкой. `find` не возвращает успешную стенограмму с потерянным оригиналом. Для такой записи можно выполнить удаление и импортировать исходник заново.

## Подключение UI

`LibraryActions` выполняет загрузку, переименование и удаление вне главного потока. `AppController` применяет результаты к состоянию и навигации. При запуске Application библиотека восстанавливается из репозитория. Переименование обновляет UI после успешной записи; удаление убирает карточку после подтверждения репозитория. Пока удаление не завершено, обработка не запускается, чтобы запоздавший callback не восстановил удалённую запись.

Статус выполнявшейся задачи и текст ошибки модели не сохраняются: после завершения процесса импорт без стенограммы снова доступен для запуска. Обработка автоматически не возобновляется; это область #8. Результат, ID, пользовательские имена и аудио сохраняются. Для корневой папки используется один экземпляр репозитория в одном процессе; конкурентная запись из нескольких процессов не поддерживается.

## Проверки

JVM-проверки включают повторное создание репозитория после удаления исходного файла, сохранение реплик и переименования, изоляцию двух записей с одинаковым speakerId, неудачную замену, обрыв копирования, пустой файл, повреждённый JSON, пропавшее аудио, неизвестную версию, дробные таймкоды, завершение временных транзакций, безопасные пути и удаление после перезапуска. Проверки контроллера покрывают восстановление готовых/необработанных записей и блокировку обработки при удалении.

Проверки на физическом устройстве и реальное заполнение накопителя пока не выполнены. Для отказа I/O при копировании используется искусственно обрывающийся поток. Сквозная ML-обработка не входит в эту задачу.

Локально прошли 44 JVM-теста, assembleDebug и lintDebug (0 ошибок; 28 предупреждений в существующем UI/ресурсах, новых предупреждений слоя хранения нет). Последний запуск был последовательным: один worker, Gradle heap 768 МБ, ограничения systemd 2 ГБ памяти / 150% CPU; пик памяти — 1,3 ГБ, swap не использовался.

Эмулятор API 36 x86_64 запускался отдельно под ограничениями systemd 3 ГБ памяти / 150% CPU / 8 минут, Android получил 1536 МБ и экран 540×960. Подтверждены сохранение четырёх демонстрационных реплик, переименование участника и восстановление после остановки процесса и перезапуска эмулятора. Настоящий rec_0055.flac импортирован через SAF, SHA-256 приватной копии совпал с исходником. После удаления внешнего тестового файла и повторного запуска в иерархии Activity появились две карточки, но UI Automator возвращал неполную иерархию: итоговое открытие импортированной записи и UI-удаление в этой проверке не подтверждены. Сохранность оригинала после удаления источника и долговременное удаление проверены JVM-тестами. В буфере crash log исключений приложения не было.
