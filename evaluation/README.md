# Оценка качества

Отдельный JVM-модуль для WER/DER, их тестов и небольших контрольных датасетов. Он не зависит от Android и не включается в APK.

- `fixtures/asr/` — архив аудио и manifest с эталонами ASR.
- `fixtures/diarization/` — аудио, метаданные и RTTM-эталоны. Происхождение, лицензии и атрибуция: [SOURCE.md](fixtures/diarization/SOURCE.md). Контрольные суммы проверяются из этой папки: `sha256sum -c SHA256SUMS`.
- `fixtures/dialogs/` — три составленных разговора по 60–90 секунд из реальных голосов Dialogs (2/2/3 участника), тексты и предварительная разметка по границам клипов. Текст независимо на слух не проверен; RTTM требует уточнения речевых границ перед оценкой DER. Источник, ограничения и пересборка: [SOURCE.md](fixtures/dialogs/SOURCE.md).
- `src/main/java/dev/wordbyword/evaluation/` — скореры WER/DER.

ASR-набор расширен в #32: `manifest.json`/`audio.zip` содержат 120 MINDS-14
(30 regression, 30 development, 60 evaluation). Эталоны MINDS местами неточны;
они сохранены без исправлений по выводу модели. `fleurs-validation.json` и
`fleurs-validation.zip` — отдельная проверка на 30 записях FLEURS validation,
не полный официальный тест и не разговоры нескольких участников. Наборы оцениваются отдельно.
- `src/test/java/dev/wordbyword/evaluation/` — тесты нормализации, формул и сопоставления участников.
- `results/` — локальные гипотезы и отчёты, игнорируются Git.
- `measure-on-device.sh` — собирает debug и androidTest APK, устанавливает их на подключённое устройство/эмулятор, получает гипотезы и сразу прогоняет оба скорера.

Гипотезы для скореров получают инструментированные тесты в `app/src/testAndroid/java/dev/wordbyword/app/evaluation/` (`DiarizationHypothesisTest`, `AsrHypothesisTest`) — они запускают настоящие `AndroidAudioPreparer`/`SherpaOnnxSpeakerDiarizer`/`SherpaSpeechRecognizer` на устройстве и пишут результат в кэш приложения. Так и должно быть: эти классы трогают `Context`/`MediaCodec`/нативные `.so`-библиотеки, а `app/src/test` исполняется против stub-jar, который на любом таком вызове бросает исключение — обычный JVM-юнит-тест этот путь не проверит.

Полный цикл одной командой из корня репозитория (нужен подключённый эмулятор/устройство, `nix develop`):

```sh
./evaluation/measure-on-device.sh
```

Скрипт устанавливает debug и androidTest APK под именами `dev.wordbyword.app`/`dev.wordbyword.app.test`, запускает оба инструментированных теста через `adb shell am instrument`, забирает файлы из `cache/` приложения через `adb exec-out run-as ... cat` (обычный способ прочитать приватное хранилище приложения без root) и удаляет оба APK при выходе — поэтому порядок именно такой: обычная задача Gradle `connectedDebugAndroidTest` сама удаляет приложение сразу после прогона, не оставляя времени забрать файлы из `cache/`.

Шаги можно повторить и по отдельности:

```sh
./gradlew :evaluation:test
./gradlew :evaluation:scoreDiarization --args='evaluation/fixtures/diarization/rec_0055.rttm evaluation/results/rec_0055.hyp.rttm 60 18'
./gradlew :evaluation:scoreAsr --args='evaluation/fixtures/asr/manifest.json evaluation/results/asr-hypotheses.json evaluation/results/asr-report.json'
```

Время `18` в примере — условное время обработки в секундах; нужно подставить измеренное для своего прогона. Без четвёртого аргумента DER-скорер не выводит RTF. Папку `results` нужно создать перед записью отчётов. Гипотезы ASR — объект с массивом `runs` (либо `samples`); каждая запись содержит `file` из manifest и строку `hypothesis`. Если есть `status`, он должен быть `READY`. Нужна ровно одна гипотеза для каждого файла manifest. Gson и JUnit — уже используемые в проекте зависимости.

Скореры оценивают готовые гипотезы и не доказывают качество моделей сами по себе отдельно от самого прогона на устройстве. Тест «эталон против себя» проверяет скорер.

Для FLEURS можно передать Android-тесту `-e archive fleurs-validation.zip -e output asr-fleurs.json`.
Четвёртый аргумент `scoreAsr` выбирает раздел MINDS: `regression`, `development` или `evaluation`.
Время каждого клипа в Android-гипотезах включает подготовку аудио, VAD и загрузку ASR.

Для сравнения на Linux есть `:app:benchmarkAsr`; нужны локальные JNI-библиотеки
sherpa-onnx 2.0.1 (`-PasrNativeDir=/путь/к/lib`). На вход подаётся заранее подготовленный
PCM16 LE, моно, 16 кГц; это исследование не заменяет Android-проверку. Например:

```sh
./gradlew :app:benchmarkAsr --args='evaluation/fixtures/asr/manifest.json evaluation/results/pcm local-models/gigaam-v2 pipeline development evaluation/results/asr-dev.json'
```

Вместо `pipeline` доступны `transducer` (NeMo RNNT/TDT) и `whisper` (int8 ONNX,
язык `ru`). В папке модели нужен `silero_vad.onnx`. Необязательные два последних
аргумента — максимальная длительность речи в секундах и контекст VAD в миллисекундах;
по умолчанию 15 и 200, как в приложении. Отчёт содержит WER/CER, RTF, хеши и гипотезы.

### Антиалиасинговый фильтр при понижении частоты (issue #45)

`LinearResampler` — линейная интерполяция без фильтра нижних частот; при понижении
частоты (44,1/48 кГц → 16 кГц) высокочастотная энергия может алиасироваться —
отражаться обратно в речевой диапазон как шум. `AndroidAudioPreparer` теперь всегда
применяет перед ресэмплингом `LowPassFilter` (оконный sinc, срез на целевой частоте
Найквиста — 8 кГц) при понижении частоты — без флага, безусловно; при частоте входа
≤ 16 кГц фильтр не создаётся, он там не нужен. До принятия решения прогоны «с
фильтром» и «без» сравнивались временным флагом конструктора (с тех пор убран) на
двух фикстурах с родной частотой выше 16 кГц (`fixtures/dialogs/`, 44,1 кГц, см.
выше, и `fixtures/asr-native-rate/`, 30 клипов Mozilla Common Voice ru/test,
подтверждённо 48 кГц через `ffprobe`, CC0-1.0) инструментированными тестами на
эмуляторе Android API 36. Результат сравнения ниже — историческая запись того,
почему фильтр включён, а не инструкция по воспроизведению (сравнивать не с чем,
второго пути больше нет).

| Фикстура | Метрика | Без фильтра | С фильтром |
| --- | --- | ---: | ---: |
| Common Voice (30 клипов, 48 кГц) | WER / CER | 1.90% / 2.05% | 1.90% / 2.05% (гипотезы побайтово идентичны) |
| dialogs (3 файла, 44,1 кГц) | WER / CER | 5.81% / 1.64% | 5.19% / 1.68% |
| `dialogs_md` | DER | 23.98% | 24.49% |
| `dialogs_ms` | DER | 51.28% | 51.30% |
| `dialogs_msd` | DER | 42.59% | 32.12% |

**Честный результат — неоднородный, не "фильтр всё решает".** На чистых коротких
фразах Common Voice фильтр не изменил ни одной распознанной буквы — на этом
материале алиасинг не оказался измеримой проблемой для ASR. На диалогах ASR
WER немного улучшился, CER немного ухудшился — в пределах шума. Диаризация:
на `dialogs_msd` фильтр явно помог и устранил переразбиение — без фильтра
кластеры `speaker_0/1/3/4` (4 вместо эталонных 3), с фильтром — `speaker_0/1/2`,
точное совпадение числа говорящих с эталоном. На `dialogs_md` DER немного вырос
(в пределах шума), на `dialogs_ms` не изменился — там диаризация и без, и с
фильтром не смогла разделить двух говорящих вообще (1 кластер вместо 2), это
не связано с алиасингом. Эффект фильтра, если он есть, проявляется в диаризации
(которая зависит от спектральных эмбеддингов), а не в ASR — согласуется с тем,
что эмбеддинги голоса чувствительнее к добавленному широкополосному шуму, чем
акустическая модель распознавания. Измерено на эмуляторе, не на физическом
устройстве; выборка маленькая (3 многоголосых файла) — не считать это
статистически надёжным выводом, только направлением.

**Решение:** фильтр включён безусловно — хуже не стало ни на одной метрике за
пределами шума измерения, а на `dialogs_msd` заметно лучше. Численного порога
для принятия решения не было: выборка маленькая, но риск включения минимален
(ASR не изменился совсем, диаризация — либо лучше, либо не хуже), поэтому
дальше не ждём.

## Сравнение последовательного и параллельного инференса

Для полного сравнения из одного запуска используйте:

```sh
bash evaluation/compare-inference.sh
```

Сценарий полностью автоматический и не использует UI: собирает оба APK и instrumentation APK, создаёт изолированный проектный API 36 AVD с четырьмя ядрами и 4096 МиБ RAM, запускает `InferenceBenchmarkTest`, который импортирует `rec_0055.flac` и вызывает тот же `AppController` и производственный pipeline, что и приложение. Скрипт снимает время pipeline и выборочные пики PSS/RSS, получает JSON из приватного каталога приложения, затем печатает сводки и diff результатов. Изолированный AVD останавливается после завершения; артефакты остаются в `evaluation/results/comparison-*`. Существующие AVD пользователя не используются и не изменяются.

Если обработка завершилась ошибкой или JSON различается, команда завершается с ненулевым кодом; логи instrumentation, logcat и выборки памяти остаются в каталоге прогона.

### Отдельный ручной замер

Нижеописанный `benchmark.sh` оставлен для ручной проверки одного уже установленного режима. Для сравнения без UI используйте `compare-inference.sh`.

Сначала соберите APK для выбранного режима (не запускайте Gradle одновременно с эмулятором на машине с ограниченной памятью):

```sh
./gradlew --no-daemon --max-workers=1 -PparallelInference=false assembleDebug
# Сохраните APK перед сборкой второго варианта.
./gradlew --no-daemon --max-workers=1 -PparallelInference=true assembleDebug
```

Установите нужный APK, подготовьте модели и импортируйте одну и ту же запись. Для каждого режима нужен необработанный экземпляр записи. Метка режима в скрипте описывает установленную сборку, но не меняет её настройки.

```sh
export ANDROID_SERIAL=emulator-5554
adb install -r app/build/outputs/apk/debug/app-debug.apk
bash evaluation/benchmark.sh parallel 60
```

После запуска скрипта нажмите «Обработать» в обычной библиотеке. Второй аргумент — фактическая длительность аудио в секундах. Скрипт перезапускает приложение, собирает logcat и PSS/RSS процесса через `dumpsys meminfo --local`, сохраняет результат в `evaluation/results/`. При ошибке или таймауте останавливает тестируемое приложение. Используйте отдельный тестовый эмулятор; по умолчанию таймаут 600 секунд (`TIMEOUT_SECONDS`).

`elapsed_ms` охватывает подготовку PCM, модели и совмещение; финальное сохранение исключено. RTF — это время, делённое на длительность записи. Последовательная контрольная сборка выполняет диаризацию перед ASR. Замеры PSS/RSS периодические, поэтому могут пропустить кратковременный пик. Они относятся к процессу приложения, а не всей виртуальной машине. Сравнивайте одинаковые образы, RAM, число CPU, модели и файлы; проверяйте также совпадение результата, а не только время.

## Разговоры и подготовка к стенду

MINDS-14 проверяет короткие банковские запросы, FLEURS — чтение, `ru-book-mix` — искусственные смеси аудиокниг.
Dialogs состоит из склеенных реплик с предварительными границами речи.
Эти наборы оставлены для регрессий; их оценки не предсказывают результат на трёх неизвестных подкастах.

Добавлены два набора:

| Набор | Случаи | Исходные разговоры | Назначение |
| --- | ---: | ---: | --- |
| [podcasts](fixtures/podcasts/SOURCE.md) | 24 | 5 | Непрерывная речь, короткие ответы, монтаж, несколько участников; development/evaluation |
| [veche](fixtures/veche/SOURCE.md) | 18 | 9 | Все сценарные встречи raw/hard, 2–10 говорящих; development |

Всего 42 случая, около 333 минут прогонов.
Это не 42 независимые записи: короткие окна входят в длинные файлы, а raw/hard содержат одни реплики.
Отчёты разных протоколов и наборов не объединяем в одно среднее.
Гипотезы моделей пока не получены: количество файлов и тесты оценщика не доказывают качество ASR или диаризации.

Подготовка требует Python 3.11+ со стандартной библиотекой и FFmpeg/FFprobe; Python-пакеты устанавливать не нужно.
Аудио и кэш игнорируются Git; в репозитории находятся эталоны, manifest и источники с суммами.
Суммарное скачивание — около 734 МБ, без моделей.

```sh
python3 evaluation/scripts/prepare_podcasts.py
python3 evaluation/scripts/prepare_veche.py
python3 evaluation/scripts/check_corpus.py evaluation/fixtures/podcasts/manifest.json evaluation/fixtures/veche/manifest.json --audio
```

После загрузки оба скрипта поддерживают `--offline`.
Версии источников зафиксированы; изменение подготовленных данных относительно manifest вызывает ошибку.

### Статус эталонов

Новые эталоны предварительные.
В podcasts опубликованы исправленные предсказания Label Studio; один файл исключён из-за восьми обратных интервалов.
В другом разговоре один повреждённый интервал исключает полный файл из оценки, но находится вне выбранных коротких окон.
В Veche тексты и время получены из сценариев и сборки добровольческих записей.
Независимая сверка на слух не выполнена; особенно важны короткие ответы, музыка, перебивания и границы речи.
Не выдаём эти таймкоды за точный ручной эталон.
Оценщик требует явный `--allow-provisional` и сохраняет этот статус в отчёте.

Изменения эталона принимаются по аудио, отдельно от сравнения моделей.
Нельзя исправлять эталон на основании того, какой вариант лучше распознал текущий GigaAM.
Для непонятного места сначала уточнить текст и границы; не придумывать слова и не убирать трудные случаи ради метрики.
После независимого ревью всей выбранной части обновить качество эталона, описание проверки и контрольные суммы.

### Совместная оценка

Для каждого выбранного `id` получить через приложение новую расшифровку и сохранить экспорт как `<id>.json` в каталоге гипотез.
Формат — обычный JSON приложения с массивом `transcript`; изменение ID говорящих вручную не требуется.
Скорер сам находит оптимальное соответствие.

```sh
./gradlew :evaluation:scoreTranscripts --args='evaluation/fixtures/podcasts/manifest.json evaluation/results/podcasts evaluation/results/podcasts-short.json evaluation short --allow-provisional'
./gradlew :evaluation:scoreTranscripts --args='evaluation/fixtures/podcasts/manifest.json evaluation/results/podcasts evaluation/results/podcasts-long.json evaluation long --allow-provisional'
./gradlew :evaluation:scoreTranscripts --args='evaluation/fixtures/veche/manifest.json evaluation/results/veche evaluation/results/veche-raw.json development raw --allow-provisional'
./gradlew :evaluation:scoreTranscripts --args='evaluation/fixtures/veche/manifest.json evaluation/results/veche evaluation/results/veche-hard.json development hard --allow-provisional'
```

Измеряются:

- **Lexical WER:** тот же нормализатор русских чисел и `ё/е`, что у ScoreAsr, без пунктуационных токенов.
  Реплики соединяются по времени начала; порядок слов при одновременной речи неоднозначен.
  Пунктуационный WER/CER остаётся в `scoreAsr`; правила организаторов неизвестны.
- **cpWER:** текст каждого участника соединяется в отдельный поток, затем минимизируется сумма редакционных расстояний по одной перестановке участников на всю запись.
  Пропущенные и лишние участники сопоставляются пустым потокам и учитываются как удаления/вставки.
  Это определённая метрика cpWER, а не произвольный SA-WER.
  Она не проверяет точность таймкодов и не равна простому WER со штрафом за ID.
  Определение и распространённый инструмент сравнения: [MeetEval](https://github.com/fgnt/meeteval).
- **DER:** интервалы реплик, collar=0, наложения учитываются, оптимальное соответствие ID независимо от cpWER.
  Если гипотеза содержит длинные ASR-сегменты, включая паузы, DER отражает это тоже.
  Для проверки самой модели диаризации использовать её RTTM и `scoreDiarization`, а не только интервалы итогового JSON.
- Число говорящих и его ошибка, составляющие DER в секундах, назначение потоков cpWER, показатели по каждой записи.

Итоговые WER/cpWER взвешиваются по числу эталонных слов, DER — по эталонному времени участников.
Недостающие, повреждённые и неуспешные результаты нельзя молча пропустить: отчёт содержит ошибки, общие метрики отсутствуют, команда завершается с ненулевым кодом.
Эталонные JSON также преобразованы в RTTM для отдельной оценки диаризации.

### Порядок сравнения на телефоне

1. Подбирать модели и параметры только на development.
   Короткие и длинные окна одного источника, варианты одной встречи и известные общие голоса остаются в одной части.
   Evaluation использовать после фиксации конфигурации; повторное использование превращает её в development.
2. На коротких файлах разбирать ASR, назначение участника и границы отдельно.
   Сравнивать один изменённый компонент за раз, затем весь конвейер.
   Ошибки экспорта, пустые результаты и падения фиксировать наравне с ошибками текста.
3. На Sony Xperia 10 V запустить длинные записи без сети с моделями из APK.
   Отдельно проверить три файла подряд через обычный интерфейс, включая импорт, новую обработку, просмотр и экспорт.
   Выбирать выпуски из разных групп; в текущей evaluation только две независимые группы подкастов, поэтому третий файл для репетиции берётся из development и не считается дополнительным независимым тестом.
4. Записать commit, SHA-256 APK, модели, Android, доступную RAM, настройки CPU, температуру/троттлинг и состояние батареи.
   Отделить холодный запуск от повторного; порядок сравниваемых конфигураций менять, чтобы не спутать качество с нагревом.
5. Снять полное время и RTF каждого файла, включая подготовку аудио и загрузку моделей, отдельно время импорта/сохранения.
   Для PSS/RSS использовать существующий `benchmark.sh` с фактической длительностью; его показатели и границы времени описаны выше.
   На длинных записях проверить отмену, потребление памяти и сохранение ID после длинной паузы.

Смена подписи участника не исправляет ошибку его назначения; хороший WER при плохом cpWER не считается улучшением всего конвейера.
Ни эти файлы, ни общий объём набора не гарантируют результат на неизвестных экспертных записях.

Из рассмотренных альтернатив [DAI-ASR-I18N](https://huggingface.co/datasets/davidai-labs/DAI-ASR-I18N) содержит русские свободные разговоры с проверенным человеком текстом, но требует согласования доступа и запрещает перераспространение.
Его не включали в загрузчики и не принимали условия от имени пользователя.
[OpenSTT Balalaika](https://huggingface.co/datasets/lab260/openstt_balalaika) использует автоматическую обработку и согласование ASR; такие тексты не становятся независимым эталоном только из-за большего объёма данных.
